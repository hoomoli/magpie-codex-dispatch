# Claude acceptance and release gate

This is the release gate for the locally installed Magpie Codex Dispatch plugin. Run it against the actual Magpie MCP gateway and installed Codex desktop, not a direct import of the implementation. Automated fixtures provide fault injection; they do not substitute for a live Claude, notification, or desktop observation.

## Outcomes and evidence

Use `PASS`, `FAIL`, `BLOCKED`, or `NOT_RUN` for every case. Never turn an unsupported step, a timeout, an accepted task, or an unreadable thread into a pass. Record automated and live evidence separately. Any FAIL, BLOCKED, or NOT_RUN in a required case keeps the release gate CLOSED. A documented product limitation can pass its boundary test; it cannot pass an unimplemented behavior.

Create a private run directory outside business repositories. Record the source commit, dirty-source hash, loaded `pluginVersion`, `loadedAt`, `moduleUrl`, desktop/CLI versions, Claude version/session ID, and timestamps. Keep exact MCP tool arguments/results in a private transcript. Exclude credentials and unrelated conversation content from reports. A source edit or plugin reload invalidates affected results; any implementation change requires the relevant regression cases and the complete release gate again.

Maintain a fixture ledger BEFORE dispatching: case, logical request ID, selected canonical project ID/cwd, title, prompt digest; append returned thread/turn IDs and notifications. Every destructive call must target an ID already recorded as created by this run. Never use IDs from earlier cleanup requests or the user's current chat. Use `MAGPIE-QA-<run>-<case>` titles and fresh UUID request IDs. A waiting creation retries identical arguments and ID, never a replacement. Keep unknown outcomes unresolved until checked.

The user has explicitly authorized `full-access` ONLY for dedicated acceptance threads and harmless marker operations inside the run directory. It does not authorize unrestricted work in existing chats. All other scenarios default to `read-only`. Do not modify product source, global settings, business files, installed credentials, or release artifacts. Do not commit, push, publish, or run bulk cleanup. Test reports/fixtures may be written under the run directory. Read applicable repository constraints before commands.

## Order, budgets, cleanup and report

1. Inventory the actual tools and local version; record source identity and existing running work without modifying it. Run A01-A03.
2. Execute M01-M09 and permissions on dedicated fixtures. Execute live interactive N01-N03 and UI U01/U02 with matching fixture IDs. Run M10/M11 during dedicated delayed turns. Each marker-only task should finish within 120 seconds; delays may take up to 180 seconds including startup. Record slow/failed cases instead of blindly resubmitting. Use at most three QA Codex turns concurrently.
3. Execute handoff/recovery and Channel tests. Handoff may wait up to 120 seconds through SAME-ID retries; stop after that with BLOCKED. Await one notification for up to 180 seconds in an interactive session, then diagnose once; no status-polling workaround to claim a wakeup pass.
4. Lifecycle tests run last. Allow at most 120 seconds for natural writer unload, then record owner_action_required and stop retrying. No restart, shared-server setup, forged notifications, lock removal, permanent deletion or shared-process kill. Preserve boundary receipts for manual finish.
5. Execute Q01 after evidence is saved. Demonstrate real Claude-to-Magpie archival and independently verify every ledger-owned QA fixture. Operator archive actions are separate manual finish and need actual confirmation; they are never plugin-success evidence. Remaining active/unknown fixtures block the gate. Preserve unrelated chats, current user chat and all audit/notification records.
6. Produce `report.md` and `results.json` in the private run directory. Include every case above, evidence paths/IDs, exact observed vs expected result, automated/live distinction, failures, limitations, remaining fixtures, and releaseGate: CLOSED or OPEN. OPEN requires every required case PASS on the same source snapshot. Never edit the matrix to hide a failure. Never publish as part of acceptance.

## Claude handoff prompt

Read this entire document and the run-specific brief. You are the acceptance reviewer, not the implementer. Execute the authorized cases using the actual Magpie MCP tools. Write only run-local reports/fixtures, preserve product code and all unrelated work. If blocked, record the precise reason and continue independent cases. Report failures for Codex to fix, then rerun affected cases and the complete gate. Do not claim native wakeups or UI behavior from a print-mode run. Keep the release gate CLOSED until all required observations exist.
